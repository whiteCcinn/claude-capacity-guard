# 故障排查

[返回 README](../README.md)

先在系统终端检查 `claude --version` 和 `claude plugin list`，再在目标 Claude 会话运行 `/capacity`。报告问题时记录使用的是 marketplace 安装还是 `--plugin-dir`，以及是否涉及子代理或 Agent Teams。

## `/capacity` 不存在

确认 `capacity-guard@claude-capacity-guard` 已启用。已有会话运行 `/reload-plugins`，或重新打开。检查是否在另一个机器、用户配置目录或独立进程中。禁用 Mods 的模式和组织策略也可能阻止加载。

如果是源码修改，先运行 `claude plugin validate plugins/capacity-guard --strict`。宿主升级后应重新生成并核对开发类型，不能只用旧声明判断成功。

## 没有额度读数

初次请求前、API Key 模式或不提供窗口的服务都可能没有 `rateLimits`。守卫不会把缺失解释成 100% 可用。首次没有已知低额度时允许请求取得读数；已有等待时暂时没有有效读数则继续等待。

不要用上下文窗口占用或本地 token 总数替代订阅额度百分比。它们衡量的是不同的事情。

## 等了很久还没有恢复

检查 `/capacity` 中的所有窗口：周额度可能比五小时窗口更晚重置。任一阻塞窗口缺少有效 `resetsAt` 时，不能计算一个可靠的统一恢复时间。

确认会话仍在运行、没有新的主任务占用它，并检查是否已进入手动状态。检查间隔会增加最多约一个周期的等待延迟；宿主忙碌、睡眠和调度也可能继续推迟执行，不能把该时间当作严格截止时间。

## 重置后仍然被限流

守卫读取的是最近响应的缓存。它不会为了检查额度调用非公开 OAuth 端点，也不能知道其他会话刚消耗多少。重置时间加缓冲经过后允许继续尝试，服务端仍可能拒绝。查看原生 `/usage`，必要时增大缓冲并等待宿主更新读数。

## 显示需要手动继续

可能原因包括进程重新打开、保存失败、停止失败、恢复指令被拒绝或交付结果不确定。先核对实际文件和外部操作，再发送新消息继续。守卫不会自动重试交付不确定的提示，避免重复工作。

`/capacity cancel` 会取消等待；持续关闭守卫需要修改 `enabled` 或禁用插件。取消后发送新任务而额度仍低，再次暂停是预期行为。

## 继续时出现翻译调用

`interaction-translator` 0.7.0 跳过 `plugin` 来源的输入。检查调用是用户手动输入“继续”引起，还是恢复后的输出翻译引起。未来翻译插件版本和其他插件可能采用不同来源策略，见[集成说明](integrations.md)。

## 主会话暂停，队友却仍在运行

本版没有整队暂停协调。分屏队友可能是不同进程，同进程队友也有独立生命周期。不要重复发送大量“继续”试图唤醒全队；先检查成员任务状态，见 [Agent Teams 边界](integrations.md#agent-teams)。

## 提交问题

使用 [GitHub Issues](https://github.com/whiteCcinn/claude-capacity-guard/issues)，提供版本、安装来源、复现步骤、期望行为、实际状态、复现是否使用模拟额度。只提供必要且脱敏的信息，不要上传凭据、完整聊天、带隐私的会话 ID、原始用户配置或任务日志。漏洞报告按[安全政策](../SECURITY.md)处理。
